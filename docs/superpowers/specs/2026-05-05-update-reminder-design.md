# 更新提醒功能设计

## 目标

为 `RATools-for-PDF` 增加一个基于 `GitHub Releases` 的更新提醒能力，满足以下目标：

- 用户可以在“关于”弹窗中手动触发“检查更新”
- 程序每天首次启动时可静默检查一次最新版本
- 仅当检测到“重大更新”时，才在启动后主动弹出提醒
- 重大更新同时支持版本规则判定和 Release 手动标记判定
- 不新增第三方依赖，不阻塞主线程，不破坏现有 UI 结构

## 当前项目现状

- 项目为 `PySide6` 桌面应用，入口位于 `main.py`
- 主界面与“关于”弹窗位于 `view.py`
- 本地设置持久化已使用 `QSettings` 写入 `settings.ini`
- 当前“关于”弹窗中的版本号为写死文本 `Version 1.0.0`
- 仓库远端为 `https://github.com/PharmaRA/RATools-for-PDF.git`

这意味着更新能力应优先复用现有 `QSettings` 和现有弹窗入口，并先统一版本来源，避免 UI 显示版本与发布版本不一致。

## 设计概览

### 1. 统一版本来源

新增一个集中版本模块，例如 `app_version.py`，作为应用版本的唯一来源，至少提供：

- `APP_VERSION = (major, minor, patch)`
- `APP_VERSION_STR = "x.y.z"`
- 需要时提供显示文本或仓库常量

以下位置统一改为读取该模块：

- “关于”弹窗版本展示
- 更新检查中的当前版本比较
- 打包版本信息生成链路
- 相关测试

### 2. 更新数据来源

更新信息来自 GitHub Releases，目标仓库为 `PharmaRA/RATools-for-PDF`。

优先使用 GitHub API 最新正式版接口：

- `GET https://api.github.com/repos/PharmaRA/RATools-for-PDF/releases/latest`

处理规则：

- 仅接收正式版 Release
- 跳过 `draft`
- 跳过 `prerelease`
- 支持从 `tag_name` 解析 `v0.2.5` 或 `0.2.5`

请求实现使用标准库 `urllib.request`，并携带基础请求头：

- `Accept: application/vnd.github+json`
- `User-Agent: RATools-for-PDF`

### 3. 重大更新判定规则

当远端版本高于当前版本时，才进入提醒判定。

重大更新满足以下任一条件：

1. 命中版本规则
2. 命中 Release 手动标记

#### 版本规则

- 当前版本主版本号为 `0` 时：`minor` 升级算重大更新
  - 例如 `0.2.5 -> 0.3.0`
- 当前版本主版本号大于等于 `1` 时：`major` 升级算重大更新
  - 例如 `1.4.2 -> 2.0.0`

#### 手动标记

Release 标题或正文中包含固定文本 `[major-update]` 时，强制视为重大更新。

该标记用于覆盖版本规则，使维护者可以对某些必须提醒的版本进行人工控制。

### 4. 交互设计

#### 手动检查

入口位于“关于”弹窗内，新增：

- `检查更新` 按钮
- 当前检查状态文本区域
- 检测到新版本时的 `打开发布页` 动作

手动检查结果：

- 已是最新版本：提示当前已是最新版本
- 检测到新版本：展示最新版本号、发布时间、Release 标题，并允许打开发布页
- 网络失败或解析失败：展示简明错误信息

手动检查不受“忽略此版本”限制。即使用户忽略了某个版本，手动检查仍然应显示真实最新状态。

#### 启动静默检查

程序启动并显示主窗口后，在后台线程中执行静默检查。

规则如下：

- 每天最多执行一次
- 仅当检测到重大更新时才弹提醒
- 普通更新不主动打扰
- 检查失败时不弹错误框，只记录为静默失败

#### 重大更新提醒弹窗

当启动检查命中重大更新时，弹出提醒框，展示：

- 当前版本
- 最新版本
- Release 标题
- 简短说明或发布时间

弹窗动作：

- `查看更新`：打开 GitHub Release 页面
- `稍后提醒`：本次关闭，不改变忽略版本
- `忽略此版本`：记录该版本，后续不再对该版本主动提醒

### 5. 本地状态持久化

继续复用现有 `QSettings` / `settings.ini`，新增 `Update/` 命名空间键：

- `Update/LastSilentCheckDate`
- `Update/LastPromptedVersion`
- `Update/IgnoredVersion`

含义如下：

- `LastSilentCheckDate`：最近一次启动静默检查日期，格式建议为 `YYYY-MM-DD`
- `LastPromptedVersion`：最近一次已弹窗提醒的版本号，用于避免同一天内重复提示同一版本
- `IgnoredVersion`：用户明确忽略的版本号；只影响启动主动提醒，不影响手动检查

抑制规则：

- 如果今天已做过静默检查，则本次启动不再重复检查
- 如果最新重大更新版本等于 `IgnoredVersion`，则不弹提醒
- 如果本次已对某个版本弹过提醒，则同一天内不重复弹同一版本
- `稍后提醒` 不写入 `IgnoredVersion`，因此未来日期仍可再次提醒

### 6. 代码结构建议

建议新增一个独立模块，例如 `update_checker.py`，避免把网络、版本比较和 GitHub 数据解析逻辑塞入 `controller.py`。

建议模块职责：

- 解析本地版本与远端 tag
- 拉取并解析 GitHub Release 元数据
- 判定是否有新版本
- 判定是否属于重大更新
- 生成结构化检查结果供 UI 使用

建议新增一个后台工作对象或线程封装，用于：

- 手动检查更新
- 启动静默检查

UI 层负责展示结果，控制层负责触发检查和处理返回值。

### 7. 数据流

#### 手动检查流程

1. 用户打开“关于”弹窗
2. 用户点击 `检查更新`
3. 控制层启动后台检查任务
4. 检查模块请求 GitHub 最新 Release
5. 返回结构化结果给 UI
6. UI 展示“已是最新版本”或“发现新版本”结果
7. 用户可点击 `打开发布页`

#### 启动检查流程

1. 主窗口显示完成
2. 控制层判断今天是否已静默检查
3. 若未检查，则启动后台静默检查任务
4. 检查模块返回结果
5. 若不是新版本或不是重大更新，则结束
6. 若命中重大更新且未被忽略，则弹提醒框
7. 用户选择查看、稍后提醒或忽略此版本

### 8. 错误处理

需要覆盖以下失败场景：

- 无网络
- GitHub API 超时
- 返回非 200 响应
- Release JSON 缺字段
- `tag_name` 不符合版本格式
- 浏览器打开发布页失败

处理原则：

- 手动检查：可向用户展示简明失败原因
- 启动静默检查：不打断主流程，不弹错误框
- 所有失败都应转换为稳定的结构化结果，避免异常直接冒泡到 GUI

### 9. 测试范围

至少补充以下测试：

- 版本字符串解析：`v0.2.5`、`0.2.5`、非法字符串
- 远端版本是否高于当前版本
- 重大更新规则判定：
  - `0.x` 阶段 `minor` 升级
  - `0.x` 阶段仅 `patch` 升级
  - `1.x` 阶段 `major` 升级
  - `1.x` 阶段 `minor` 升级
- `[major-update]` 标记识别
- 忽略版本与静默检查节流逻辑

测试尽量覆盖纯逻辑函数，减少对 GUI 和真实网络的依赖。网络层应通过 mock 返回值测试。

## 非目标

本次不包含以下内容：

- 自动下载更新包
- 自动覆盖安装
- 增量更新或内置升级器
- 多更新源切换
- 预发布版本订阅

## 实施顺序建议

1. 提取统一版本模块并修正现有版本展示
2. 实现版本解析与重大更新判定的纯逻辑函数及测试
3. 实现 GitHub Release 拉取与结构化返回
4. 在“关于”弹窗接入手动检查更新
5. 在启动流程接入每天一次的静默检查与重大更新弹窗
6. 补齐忽略版本和提示抑制逻辑测试

## 验收标准

- “关于”弹窗显示真实应用版本，不再使用写死版本号
- 用户可手动点击“检查更新”并得到明确结果
- 启动静默检查每天最多执行一次
- 仅重大更新触发启动提醒
- `[major-update]` 标记可以强制触发重大更新提醒
- 用户忽略某版本后，该版本不再主动弹出
- 手动检查始终能看到真实最新状态
- 网络失败不会导致程序卡死或启动报错
